# Catalog Review Policy

The catalog is curated, not exhaustive.

## Evidence tiers

| Tier | Requirement |
|---|---|
| A | Official standard, regulator, foundation or maintained project documentation |
| B | Maintainer-controlled repository or vendor documentation |
| C | Community documentation with a clearly identifiable upstream |
| D | Unverified claim, mirror, fork or secondary article |

Core catalog entries should normally have Tier A or B evidence.

## Promotion criteria

A watchlist item may be promoted when all of the following are known:

- canonical upstream;
- current maintenance state;
- license or commercial model;
- correct category;
- supported domain;
- primary use case;
- meaningful documentation;
- review date;
- relationship to existing frameworks / platforms.

## Deprecation criteria

Move an entry to legacy when:

- the canonical project is archived;
- the maintainer recommends a successor;
- the project is materially incompatible with current platforms;
- upstream documentation disappears;
- a project remains historically important but no longer belongs in a current workflow.

## Naming rules

Do not label every project a framework.

Use:

- `methodology`
- `knowledge-base`
- `standard`
- `assessment-guide`
- `emulation-platform`
- `validation-platform`
- `assessment-tool`
- `operational-platform`
- `detection-format`
- `hunting-platform`
- `data-collector`
- `attack-path-analysis`

## Review cadence

- regulators / standards: every 6 months;
- fast-moving AI and cloud projects: every 90 days;
- community offensive tooling: every 90 days;
- commercial platforms: every 6 months;
- legacy entries: annually.

Every machine-readable entry should carry or inherit a review date.
